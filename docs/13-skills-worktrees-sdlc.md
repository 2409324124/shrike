# 13 · Skills, worktrees, SDLC and the hidden power moves

Owner's direction (2026-10-08): Shrike is a visual tool for vibe coders, so the features power users love but most people never find (in Claude Code, in Orca, in niche workflows people share online) go in **obvious places and flows**. Specifically: a skill library that evolves, GitHub skills (merge, conflicts, PR review), Orca's worktrees, driving apps automatically the way the owner does with the chrome-devtools MCP, and the whole SDLC.

## The principle: make the hidden move the obvious next button

Power users have muscle memory for moves like "rewind", "plan first", "think harder", "try it in a worktree", "save this as a skill". Vibe coders don't know these exist. Shrike shows them **at the moment they're useful**, as one plain-words button, never in a settings page:

| Moment in Shrike | Hidden move | The obvious button |
|---|---|---|
| A fix didn't work | Claude Code rewind (Esc Esc) | **Rewind to before this fix** on the trip |
| The agent is about to change several files | Plan mode (Shift+Tab) | **Plan first** toggle on the composer, on by default for multi-file changes |
| A bug is subtle | Extended thinking ("ultrathink") | **Think harder** dial (Quick, Normal, Deep) on the composer |
| Two fixes look plausible | Parallel worktrees (Orca), subagents | **Try both** (fix race in worktrees) |
| You solved something you'll hit again | Skills | **Save as a skill** after a verified fix |
| Long work | Background tasks, /loop, routines | **Keep watching** (re-run this flow every N minutes or on every save) |
| You want a second opinion | /code-review, /security-review | **Review this fix** before Apply |
| Context is filling up | /compact, /context | The fuel ring (A7) turns amber and offers **Tidy up the agent's memory** |
| You'll ask the same thing again | Custom slash commands | **Save as command** from any Ask |
| You want to resume yesterday | --continue / /resume | **Pick up where you left off** on the welcome screen |

| S4 | **Evolving skills, gated on the outcome** | Every skill-driven action declares its expected outcome (`load_skill` says "Done when"): run → app_ready passed and every health check done; debug/fix → patch applied and the failing trip passes again ("Fixed and verified"); flow → the flow's next replay all green; ship → PR open and checks green (or pushed, when the repo has no `.github/workflows`; a merge counts too); conflicts and sync → merge clean and the saved flows pass; CI fix → checks green; review → the review run finished; quest → every objective's flow passes (QB7); review lessons → a reviewer resolves a thread behind the draft or approves one of your PRs after it, without the issue coming back (RL4). Outcome missed: drafts stay pending and the System says once, quietly, "Not learned: the app never came up"; a later verified run of the same skill promotes them. A draft settles only on outcomes in the project it was drafted in; for ship and CI that means this project's PR checks changing to all green (or red), not a PR that was already green. Undo refuses when the file was edited after the level up. No Keep step (`answerSkillProposal` can only discard). The skill sheet's history lists pending drafts with **Edit before keeping** (opens a copy in `.shrike/skill-drafts/`; what's there is what gets kept) and Undo on level ups | Build |
| S5 | **Save as a skill** | After a verified fix or a successful flow, one button turns the steps into a new skill draft (name, when, steps) | Build |
| S6 | **Skill chips in Ask** | The agent column shows which skill it loaded (A4, already built); typing `/` lists skills alongside commands | Build |
| S7 | **Skill marketplace** | Share and install skills from others | Design |
| S8 | **Action recipes** | Orca-style, a Recipes tab on the shelf (also `/recipes` and voice "recipes"). One card per action (Get it running, What happened, Fix, Flow review, Commit message, Pull request details, Branch name, Commit failure fixes, Push failure fixes, Broken checks, Conflict resolution, Merge when green, Sync main, Review PR), one line until clicked. Open: agent picker (default, Claude Code, Built-in; Claude Agent Teams, Codex and OpenCode shown disabled until Shrike can start them), CLI arguments (only `--model` and `--fallback-model`; kept with the recipe, not yet passed to the agent, and the card says so), the prompt template with clickable variables (`{basePrompt}` is the skill body; a variable nobody fills stays visible; wired actions default to `{context}`, since the agent loads the skill itself through `load_skill`, which is what counts its uses), and the skill behind it (level, rank, uses, last evolved, changelog, view only). A save keeps only what differs from what that scope inherits (built-in for your default, your default for a project), so evolving built-ins and later edits to your default still flow down, and a project can still pick built-in values over your default. Reset is one step back: Reset this project clears the project's recipe, Clear my default clears yours. Wired today: Review PR, Conflict resolution, Broken checks, Commit message (the Changes dock's Write it for me, SC3) (`main/recipes.ts` `resolveRecipe`); the rest show Soon until their call sites hand the action to an agent | Build |

## MCP · Your agent's tools (the MCP hub)

Owner's ask (2026-10-09): "what about MCP? how are we managing them? This is an app for vibe coders, without MCP it's not fair." Before this, Shrike only read Claude Code's MCP config (`~/.claude.json` user and `projects[root]`, the project's `.mcp.json`) and passed it through behind the B4 toggle. The hub makes every server visible, checkable and addable, in plain words, without ever touching Claude Code's own files.

Where servers come from, highest first (the same name lower down is hidden, and the card says so): **Shrike's own** for this project (`<project>/.shrike/mcp.json`), Shrike's own for you (`~/.shrike/mcp.json`), then Claude Code's: local (`~/.claude.json` `projects[root]`), project (`.mcp.json`), user (`~/.claude.json`). Shrike's own beat Claude Code's because Shrike can't change those, so a copy in Shrike is how you change one. Shrike writes only its two files; `~/.claude.json`, `.mcp.json` and anything under `.claude` are read-only. Shrike's files use Claude Code's format, with `${NAME}` where a secret goes; the values live in userData `mcp-secrets.json`, encrypted with Electron `safeStorage` (the macOS keychain), and are filled in only in the 0600 temp config a run gets. Per-project switches, trust and dismissed suggestions live in userData `mcp-state.json` (`main/mcp.ts`, Electron-free; `ipc.ts` brings the keychain, the approval card and the guarded shell).

| ID | Element | What it is | Status |
|---|---|---|---|
| MCP1 | **Tools tab** | A right-dock tab (Tools, a plug), also opened by the My tools chip's plug button, `/tools` and voice "tools" ("my tools", "mcp servers"). Groups: From Claude Code, This project's .mcp.json, Shrike's own. One line on top says how many are ready and holds the same switch as the My tools chip ("Your agent gets these when you ask"). Opening it runs a health check of every server that is on and trusted (once per 5 minutes; Check all forces it): start it (stdio) or connect (http, sse) with the MCP SDK, list its tools, close it; 20s timeout; the server's whole process tree is killed after, so nothing is left running. ## L · The SDLC rail

One slim rail across the top of the Thread (only when there's something in flight) showing where a change is in its life, left to right:

**Spot → Understand → Fix → Prove → Review → Ship → Watch**

| ID | Stage | Lights up when | Status |
|---|---|---|---|
| L1 | Spot | A trip broke (or a flow in B3 turned red) | Build |
| L2 | Understand | The agent reported a finding (FOUND IT) | Build |
| L3 | Fix | A patch was applied (checkpoint A6), or a worktree fix exists (W3/W4) | Build |
| L4 | Prove | The re-run trip and the saved flows went green; unit tests ran if the project has them (`npm test` detected) | Build |
| L5 | Review | Code review (G2-style on the local diff) and security review passed or were waived | Build |
| L6 | Ship | PR opened (G1), CI green (G4), merged (G5) | Build |
| L7 | Watch | The flow is in Keep watching (B3) | Build |

Each stage is a dot with one word; the current stage glows; clicking a stage opens its detail (the trip, the finding, the diff, the test output, the review, the PR). ADHD-first: the rail is hidden when nothing is in flight, and only the current stage is bright.

The rail has a second mode, **Build**, for making something new (QB below): **Idea → Plan → Design → Build → Prove → Review → Ship → Live**. It switches by itself: a broken trip in focus shows Fix, a quest in flight shows Build; a small Fix / Build toggle at its left end overrides that until what's in flight changes.

## C · Conversation branches (an advanced `/btw`)

The owner's long-wanted feature: when talking to the agent, the next question shouldn't always pile onto the bottom of the session. You should be able to **branch** the session to think differently, while the main session stays untouched. Claude Code's `/btw` asks a side question without adding to context; this goes further.

Mechanism: Claude Code's `--resume <session> --fork-session` copies a session under a new ID and leaves the original untouched. Branching from an **earlier** step has no CLI flag, so Shrike forks from the latest point and tells the branch to set aside everything after the chosen step ("Ignore what happened after step 4 and think differently: …"). ponytail: a truncated copy of the session would be exact, but its file format is internal to Claude Code; upgrade when an official "resume at message" option exists. The built-in brain branches exactly (its messages are Shrike's own).

| ID | Element | What it is | Status |
|---|---|---|---|
| C1 | **Branch from here** | On any agent step (a message, a finding, a proposed fix), a small fork icon: name the branch (optional) and ask the different question. A new run starts from that point; main is untouched | Built |
| C2 | **Branch map** | A tiny subway at the top of the agent column: the main line plus one coloured line per branch peeling off at its step, each with a name and a state dot (thinking, found, fixed, stopped). Click a line to switch; the current line glows. Hidden when there is only main | Built |
| C3 | **Aside** (`/btw`) | A one-off question that never enters any session: forks at the latest point, the answer appears in a dismissible bubble, with **Keep as a branch** if it turns out to matter | Built |
| C4 | **Compare branches** | Two branches side by side: each one's finding, proposed fix diff and re-run result, with the differences highlighted | Built |
| C5 | **Bring it back** | Carry a branch's conclusion into main as one short message ("Another line of thinking found: …"), or adopt its fix | Built |
| C6 | **Code stays separate** | A branch that changes code automatically gets its own worktree (W*), so main's code is untouched too; its re-run trips carry the branch colour | Built |

## R · Get it running, and the core principle: every action becomes an evolving skill

**The principle (owner, 2026-10-08): every action starts with a skill and ends with a skill, Claude drives it, and it is as visual as possible. Ever-evolving skills plus intuitive visuals are the whole premise of Shrike.**

 Shrike is for vibe coders, and vibe coders work through prompts. For prompts to keep getting better, everything that worked must be stored as a skill, working patterns must be recognised across projects, and skills must keep being populated and evolved. **Every kind of action in Shrike (start, debug, fix, seed, test, ship, review, flows) produces or improves a skill.** Successful runs are consolidated; new fixes become drafts (S4) that Shrike keeps by itself only once the action's expected outcome is verified; patterns that recur across projects ("Python services in these repos need `uv run`", "process-compose needs PC_DISABLE_TUI=true when backgrounded") become personal skills that later projects start with.

**What went wrong before (xyne-spaces, 2026-10-08):** the old start was a one-shot guess (package.json `dev:*` scripts, workspaces, Procfile) followed by "Your app didn't start". It picked an interactive menu script (`pnpm dev:all`) and a Python `uvicorn` service whose binary wasn't on PATH, and ignored the repo's own `.claude/skills/run-xyne-spaces/SKILL.md`, which describes exactly how the app starts (Nix infra via `PC_DISABLE_TUI=true just services`, `pnpm install` + `build:shared`, backend :3001, dashboard :5173, smoke check). No prerequisites, no fixing, no learning: a dead end.
